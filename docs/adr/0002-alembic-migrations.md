# 0002: Versioned schema with SQLAlchemy models and Alembic

- **Status:** Accepted
- **Date:** 2026-11-21

## Context
The first schema was a single `schema.sql` run by Docker's init script. That only runs when the
database volume is empty, so the schema could never change without deleting all data; there was no
version history, no path to apply changes to the hosted database (M3), and no rollback.
Liquibase was considered because it is a familiar standard in Java teams.

## Decision
Define tables as SQLAlchemy 2.0 models (`src/catalog_copilot/db/models.py`) and manage every schema
change as an Alembic migration in `migrations/versions/` (`0001_create_products_table.py`, ...).
`alembic upgrade head` applies pending migrations in dev, CI and production alike. The database
URL comes from app settings (`CC_DATABASE_URL`), never from `alembic.ini`.

Alembic over Liquibase: it is Python-native (no Java runtime in dev or CI), and it compares
migrations with the models (`alembic check`, autogenerate), so drift between them is caught.

## Consequences
- Schema changes are reviewable, reversible (`alembic downgrade -1`) and recorded in
  `alembic_version`.
- Autogenerated migrations must be reviewed by hand; 0001 needed a missing pgvector import and
  `CREATE EXTENSION vector` added manually.
- An integration test asserts the models and migrations match.
- If a Java service ever shares this database, revisit the tool choice so both teams use one.
